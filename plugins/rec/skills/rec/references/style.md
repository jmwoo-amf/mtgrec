# 회의 요약 문체

`config.json` 의 `style` 이 비어 있을 때 요약 에이전트가 읽는 기본 문체 규격이다. 팀에 자기 문체 가이드가 있으면 `style` 에 그 파일 경로를 넣는다. 그때는 이 파일을 읽지 않는다.

## 종결

| 자리 | 문체 |
|------|------|
| `## 회의 결론` | 개조식 또는 짧은 문어체 |
| 카드의 배경 · 내용 · 결론 | 개조식(음슴체): `판단해 왔음`, `확인 필요함`, `미결` |
| 액션플랜 | 개조식. 무엇을 할지 동사로 끝낸다 |

한 카드 안에서 문체를 섞지 않는다. `판단해 왔음` 과 `전달한다` 를 같은 카드에 두지 않는다.

## 하지 않을 것

- 이모지를 쓰지 않는다
- em dash(—)와 en dash(–)를 쓰지 않는다. 쉼표, 콜론, 괄호로 붙이거나 문장을 나눈다
- 과장 표현을 쓰지 않는다: `완벽한`, `훌륭한`, `획기적인`
- 문서가 자기를 설명하지 않는다: `본 회의록은 ~를 정리한 것입니다`, `아래와 같습니다`, `정리하면`
- 사실을 적은 뒤 그 성격을 다시 규정하지 않는다: `~하는 이유입니다`, `~는 의도된 것입니다`, `결국 ~인 셈입니다`
- 문서 끝에 요약 · 마무리 절을 두지 않는다. 결론은 이미 맨 앞에 있다
- 전사본에 없는 후속 제안을 액션플랜에 보태지 않는다

## 할 것

- 숫자 · 날짜 · 식별자는 실제 값으로 쓴다. `여러 개`, `일부` 대신 `3개`, `2건`
- 항목 하나에 사실 하나. 두 문장이 되면 항목을 나눈다
- 추측 · 해석은 완충 표현으로 밝힌다: `~것으로 보임`. 사실 진술에는 붙이지 않는다
- 기술 용어는 원어를 그대로 쓴다. 한글 용어에 원어를 괄호로 병기한다: `인터페이스(UI)`
- 강조는 **볼드** 로만 쓴다. 한 카드에 볼드 1개 이하

## 표본

고칠 것:

```
### 1. PoC 장비

- **배경:** PoC 장비에 관하여 논의가 있었습니다
- **내용:** 여러 가지 방안이 검토되었습니다
- **결론:** 추후 논의하기로 하였습니다
```

고친 것:

```
### 1. PoC 에 어떤 모델을 몇 대 투입할 것인가

- **배경:** 고객이 물류센터 지게차 충돌 방지 용도로 실내 테스트를 요청함
- **내용:** 2대로 시작하자는 쪽과 커버리지 때문에 3대가 필요하다는 쪽이 갈림
- **결론:** 미결. 감지 범위 도면을 받은 뒤 정하기로 함
```
